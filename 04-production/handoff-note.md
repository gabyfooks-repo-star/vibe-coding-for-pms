# Engineering Handoff Note

> Module 4 · Production Specs. Open the black box, make the build legible to an engineer.

## What this is

_One paragraph an engineer can read in 60 seconds._

This is a React + TypeScript front end for a decision-first analytics dashboard that shows how much of Houselights' ticket buying comes from the mobile app versus the web, by region and date range. It has three pages (Channel share, Revenue, Retention), a detail page for each chart, and a brief that turns the one recommended action into an experiment or review ticket. There is no backend: every number comes from a hard-coded table in src/data/, the “fetch” is a 900 ms timer, and nothing is saved or sent. The code has never been run: it was refactored from a single-file prototype on a machine without Node.js, so expect the first npm run typecheck to need small fixes. The calculations and screen logic are worth keeping; the data layer is the part to replace. Start with How to run it, then Solid vs. duct tape. The product context is in the PRD (PRD: Decision-first channel dashboard), and the hypothesis it tests has not been validated yet.

## Architecture (plain language)

- **Frontend:** • Stack: React 18, TypeScript (strict), Vite. No router, state library or UI kit. • Navigation: src/app/App.tsx keeps a route value (which screen, plus the chart or region it needs) and switches between six screen components. Page tabs and bottom links change the route; nothing ever ends on a dead-end screen. • Shared state: only four values live in App: route, region filter, date range, and the prototype's Simulate setting. Region and date range carry across every page. Small interface state stays inside its component: the calendar's draft range, the line chart's hover, the brief's owner. • Folders: one per PRD screen under src/features/ (channel-share, revenue, retention, chart-detail, action-brief, why-this-design). Each holds its components and a *.model.ts view model. Pieces used by several screens are in src/shared/.
- **Backend / data:** There is no backend today; everything below is mocked in the browser. • src/data/regions.ts: hard-coded 30-day totals per region (Oct 6 – Nov 4, 2026): referrals, purchases, average fee per purchase, and retention cohort counts. • src/data/dailySeries.ts: generates made-up daily values for Jan 1 – Nov 4, 2026, scaled so the default range matches the totals. This is what makes the date filter work. • src/data/channelDataSource.ts: a fake fetch that waits 900 ms and returns ready, empty or error. • src/metrics/metrics.ts: computeMetrics(region, range) returns every figure the screens use. It is pure and works the same on real data. What production needs from a backend: daily referrals, purchases and gross ticket fees by region and channel for a date range, and repeat-buyer counts for a retention cohort.
- **Key flows:** 1.  Opening Channel share: useChannelData calls fetchChannelData. The page shows a skeleton, then exactly one of: the data, the empty message, or the error message. A newer request aborts an older one.
2.  Changing a filter: a region tab or the date picker's Apply updates App state. Every view model recalculates from computeMetrics; Channel share also reloads through flow 1.
3.  Acting on the recommendation: recommendation.ts picks one action per region by fixed rules and estimates its impact. Clicking it opens the brief with that region; confirming only changes local state.
4.  Opening a chart's detail page: clicking a chart or its Details button sets the route to that chart. buildChartDetailView builds the figures, chart geometry, insights and table; the line chart keeps its own hover state.

## Risks & assumptions for the team

The biggest risk is that the code has never run; the biggest assumption is that real data looks like the mock.
Risks
• Never compiled or run. Written without Node.js. A script checked that every import resolves to a real export and every CSS class exists, but types, rendering and interactions are unverified.
• Calculations in the browser. computeMetrics sums daily arrays and is called many times per render (once per region row, per table). Fine for four regions and 308 days; with real data volumes, move the aggregation to the backend.
• No routing. Screens are switched in state, so the browser back button, deep links and page refresh all return to Channel share. Add a router before anyone shares links.
• Dates are local time. Day numbers are converted with the browser's time zone. Real data will need one agreed time zone (likely the event's or UTC).
• Fixed year. Dates, presets and the calendar assume 2026 and data through Nov 4, 2026 (src/data/dates.ts).
• Recommendations could mislead. Fixed rules and a 5% shift assumption produce confident-looking estimates. The page labels them as upper bounds, but someone needs to own and validate them.

Assumptions to confirm (also open in the PRD)
• Referral: a session that enters the purchase flow, credited to the channel where it started; no cross-device stitching.
• Gross ticket fees: service and order fees on top of face value, before refunds and payment costs.
• Retention: another purchase within 6 months of the first purchase in the cohort; the cohort is fixed (Apr 6 – May 5, 2026) and ignores the date filter.
• Regions: four regions are enough for version 1; no country drill-down.
• The hypothesis: that a decision-first first screen reduces bounce and gets the action clicked. It has not been tested with users, and nothing in this code measures it yet.

## How to run it

```
You need Node.js 18 or later and the houselights-dashboard folder. It isn't in a repository yet, so ask the product owner for a copy.
1.  Install packages: npm install (React 18.3.1, Vite 5.4.10, TypeScript 5.6.3, all pinned in package.json).
2.  Type-check first: npm run typecheck. This is the first time the code has been compiled, so fix what it reports before anything else.
3.  Start it: npm run dev, then open the local address Vite prints.
4.  Build for production: npm run build (type-checks, then writes dist/).
Once it runs, check these by hand:
[ ] Channel share shows the skeleton, then 48.6% for All regions on the default range (Oct 6 – Nov 4, 2026)
[ ] The Simulate menu in the dark bar shows the empty and error states, and Refresh recovers
[ ] Region tabs and the date picker update every figure, and carry across pages
[ ] Each of the six charts opens its detail page, and the line charts respond to hover and arrow keys
[ ] The recommended action opens a prefilled brief, and confirming shows the simulated confirmation
[ ] Every screen has a way back to Channel share
Reference material: the project's README.md maps every function in the original Main.dc.html to its new file. The original prototype is still published as a working click-through, and is the source of truth for intended behaviour until this version runs.
```
